# Setup

The existing Supabase project has already applied [schema.sql](../supabase/schema.sql) and the [vector upsert migration](../supabase/migrations/20261016_vector_upsert_grant.sql). Do not rerun them on that project. The two workflows have been tested in n8n Cloud. This guide is for a fresh deployment or a new local import.

## Database

1. Enable pgvector and run [schema.sql](../supabase/schema.sql) once in a fresh Supabase SQL Editor. It creates `public.documents`, `public.document_registry`, `match_documents`, `rag_private.activate_document`, the `rag_chat` schema, indexes, grants, and RLS. Fresh deployments do not need the separate upsert migration because its grant and trigger are included in the schema.
2. Create a dedicated PostgreSQL login and grant it the schema's `rag_workflow` role. Choose a unique password outside this repository:

   ```sql
   create role rag_n8n_login with login inherit password '<YOUR-UNIQUE-PASSWORD>';
   grant rag_workflow to rag_n8n_login;
   ```

3. Configure an n8n PostgreSQL credential for that login. For Supabase's session pooler, use its dashboard host and project reference, port 5432, database `postgres`, SSL, and username `rag_n8n_login.<PROJECT-REF>`. The PostgreSQL login reads the registry, invokes activation, and owns its chat-history table in `rag_chat`. It has no direct write grant on `public.documents` and no CREATE grant in `rag_private`.
4. Configure an n8n Supabase credential with the project URL and the server-side legacy `service_role` key. Store the key only in n8n's credential manager. The vector store inserts into `public.documents`; its LangChain upsert path requires UPDATE privilege on `content`, `metadata`, and `embedding`. The schema's trigger rejects direct updates to existing rows.

The read-only [verify.sql](../supabase/verify.sql) checks objects, grants, RLS, and active chunk counts. Do not paste query output containing document text or identifiers into a public issue.

## Workflows

Import the [ingestion](../workflows/01-document-ingestion.review.json) and [chat](../workflows/02-conversational-assistant.review.json) review copies as new, inactive workflows. They contain no credentials or live webhook IDs. The root-level source exports are local-only and should not be imported for this deployment.

Attach credentials in n8n:

| Credential | Nodes |
| --- | --- |
| Supabase `service_role` | `Index Chunks in Supabase`, `knowledge_base_search` |
| Dedicated PostgreSQL login | `Check Document Version`, `Confirm Duplicate`, `Activate Document Version`, `Postgres Chat Memory` |
| Existing n8n Gateway OpenAI | Chat model and both embedding nodes |
| Existing n8n Gateway Brave | `web_search` |

The embedding nodes use `text-embedding-3-small` with 1536 dimensions. The chat model selector in the export is `gpt-6-luna`; check model availability in the target n8n environment. The chat memory table is `rag_chat.chat_histories`. The Brave community node must be available in the target n8n instance.

The upload form uses n8n User Auth and execute access. The chat trigger is private and supports n8n's built-in editor Chat UI. Its session validator requires a valid session ID and does not treat a client-supplied user ID as authentication. Keep both endpoints private until access controls and hosting-level request limits are reviewed. The in-workflow upload limit is three files of 5 MiB each and runs after n8n receives the request.

The two review exports omit n8n credential references and webhook IDs. Reconnect credentials after import and verify the trigger URLs generated by that n8n instance. Do not replace Gateway credentials with a personal OpenAI key.

## Maintenance

If indexing fails, staged chunks can remain inactive. Investigate the failed execution before cleanup. An administrator can preview inactive chunks older than seven days with a query based on the registry's active version, then call `public.purge_abandoned_chunks` after confirming they are abandoned. The function is restricted to administrator use and can briefly block ingestion. See [schema.sql](../supabase/schema.sql) for its implementation.

If an upload reports `conflict_retry`, retry that file. It means the registry changed while duplicate status was being checked. Concurrent replacements serialize at activation; the last successful activation becomes active.

Run `npm test` for offline checks. The [testing notes](testing.md) separate observed live behavior from untested failure and performance cases.
